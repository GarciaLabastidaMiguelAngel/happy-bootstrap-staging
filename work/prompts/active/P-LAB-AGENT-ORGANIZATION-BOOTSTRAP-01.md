1. CAPABILITY COVERAGE BEFORE AGENT COUNT
============================================================

Do NOT begin by deciding how many Agents exist.

First build a capability/responsibility coverage model:

OBJECTIVE
-> REQUIRED CAPABILITY
-> RESPONSIBILITIES / POLICIES / GOVERNANCE
-> DETERMINISTIC CONTROLS
-> TOOLS
-> SKILLS / PROCEDURES
-> EXECUTION WORKSTREAMS
-> AGENT / SESSION TOPOLOGY IF JUSTIFIED.

Distinguish rigorously:
- AREA = logical responsibility/capability grouping;
- WORKSTREAM = current execution grouping;
- SESSION = ephemeral provider execution context;
- TOOL = bounded deterministic capability;
- SKILL = reusable procedure;
- AGENT = autonomous/semi-autonomous execution role justified by persistent reasoning/orchestration need.

For every major capability record:
- objective served;
- responsibilities;
- policies/gates;
- standards/evidence;
- deterministic controls;
- Tools/Skills required;
- AI reasoning need;
- human authority need;
- information sensitivity;
- environment/mode;
- dependencies;
- outputs;
- metrics/maturity;
- current execution owner.

First guarantee CAPABILITY COVERAGE. Then optimize the number of sessions/agents.

No responsibility may disappear when a role/session/agent is merged or removed. Name the successor Tool/Skill/Agent/service/owner and validate state/work transfer.

7. INFORMATION CLASSIFICATION / SENSITIVE DATA
============================================================

Create an explicit information-governance workstream and deterministic handling-policy model.

Do not use one vague `sensitive=true` field.

Distinguish:
- business sensitivity;
- data category;
- regulatory/control scope;
- handling attributes;
- environment;
- action/projection.

Institutional classification policy is authoritative when available.

Research whether Microsoft Purview sensitivity labels are institutionally used/authoritative for Office 365/SharePoint/OneDrive and, if so, map/integrate them instead of inventing a conflicting taxonomy.

Access decision must consider:

identity
+ role/entitlement
+ environment
+ information classification
+ requested action
+ purpose/context
+ policy/gates
+ optional step-up/approval
-> ALLOW / DENY / REQUIRE_STEP_UP / REQUIRE_APPROVAL / MASK / REDACT.

Do NOT conflate:
- LDAP/directory;
- authentication;
- MFA/step-up;
- authorization.

LAB may expose sensitive information only when authorized and justified. PLATFORM_DEV should prefer synthetic/masked data. Future SERVICE/preprod/prod must bind to the approved enterprise identity/authentication/authorization pattern.

Before copying data into any of these, run handling policy:
- Devin/provider knowledge;
- prompt/context pack;
- Lucene/vector;
- graph projection;
- logs/traces;
- Arc42;
- Confluence;
- Excel/PPT/PDF exports.

Default is NOT to copy raw sensitive data merely because technically possible.

PCI:
- do not assume the whole platform is PCI in scope because it is used by a bank;
- determine actual CHD/SAD/CDE-impact scope;
- minimize PCI scope by default;
- prefer tokenized/masked/CardID representations;
- do not persist PAN/PIN/SAD for knowledge/search convenience;
- do not send payment data to Devin or telemetry by default;
- use official PCI SSC requirements/guidance and institutional policy.

Backups/snapshots must carry classification/retention/access/restore rules too.

============================================================

The same product must remain useful even if OpenShift DEV has no central DB.

Preserve:
- Git = declarative/governed definitions and reconstructable inputs;
- local embedded stores = workstation mutable state/read projections;
- OpenShift DEV without DB = Git-derived projections + explicitly temporary/degraded mutable state;
- future central persistence = selected shared/mutable authority after migration analysis.

Do NOT use Git as a high-frequency transactional DB.
